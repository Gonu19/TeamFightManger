## D57. `common.data` 를 이름 출처에서 뺀다. 선수 이름은 에셋의 이름 풀에 있다 (2026-08-29)

**선수 이름을 찾다가 팀 이름 쪽 실수를 발견했다.**

**선수 이름은 참조다.** 세이브의 `Athlete.Name` 443개가 전부 `` `33 `` 같은 백틱 형식이고,
세이브 안에 한글 문자열은 단 하나(`고감독` — 감독 이름)뿐이다. 게임 에셋
(`sharedassets0.assets`)의 로컬라이제이션 JSON에 `"names"` 배열이 있고, 백틱 뒤 숫자가
그 인덱스다.

```
"names": ["Faker", "Score", "PraY", "Deft", "Smeb", "Kuro", "Bang", "Mata", ...]
```

팀 이름과 **같은 구조**다 — 세이브는 참조만 들고, 표시 문자열은 에셋에 있다.

**그 김에 팀 이름 로컬라이제이션도 찾았다.** 아까 못 찾은 이유는 키가 점으로 이어진
평면 문자열이 아니라 **중첩 객체**였기 때문이다.

```
"name": { "pro": { "team8": "Strange Seals", ... }, "worlds": { "team15": "Wet Whale Sharks" } }
```

**즉 게임 기본 팀 이름은 동물 이름이다.** 사용자가 화면에서 읽어 준 목록
(`T1` · `KT Rolster Bullets` …)은 기본값이 아니라 **그 사람 게임에 적용된 커스텀**이다.
사용자가 실물로 확인해 준 값이므로 시드는 그대로 둔다 — 화면에 그렇게 보이는 것이 사실이다.

**그런데 이것이 `common.data` 폴백의 근거를 무너뜨렸다.** D56 은 "딕셔너리 키가 곧
`game_team_id`" 라고 썼는데 **확인된 적이 없다.** 실측은 반대를 가리킨다:

| | `common.data` 키 1 | 세이브 `TeamInfo` 1 |
|---|---|---|
| | `OKSavingsBank BRION` | `team.name.amateur.team1` |
| | 프로팀 이름 | 아마추어 1번 자리 |

키 42 는 `T1` 인데 세이브의 42번은 `worlds.team5` 다. **안 맞는다.**

**결정 — 이름 출처에서 `common.data` 를 뺀다.** 세이브가 모르는 번호는 이름을 붙이지 않는다.
**틀린 이름은 없는 이름보다 나쁘다** — 화면에서 둘이 구별되지 않고, 틀린 쪽은 사용자가
그것을 사실로 읽는다. D51(티어 컷라인)·D56(시드에 없는 키)과 같은 원칙이다.

`CommonDataParser` 는 지운 게 아니라 **안 부른다.** 프로필의 커스텀 로스터를 읽는 유일한
경로이고, 그 키의 의미가 밝혀지면 되살릴 자리다 — D53 이 `merge` 함수 둘을 남긴 것과 같다.

**교훈 — 두 번째로 같은 실수를 했다.** D56 에서 팀 번호 매핑을 바이트로 추측했다가
파서로 뒤집혔고(키 7 은 `T1` 이 아니라 `Najin White Shield` 였다), 이번엔 그 추측 위에
세운 폴백이 무너졌다. **틀린 추측을 지운 자리에 그 추측에 기대던 코드가 남아 있었다.**
추측을 고칠 때는 그 추측을 쓰던 곳을 같이 훑어야 한다.

**다음.** `"names"` 배열을 시드로 뽑으면 선수 적재가 열린다. 팀 이름 시드와 같은 모양
(`athlete_name_seed(idx, name)`)이고, `Athlete.Name` 의 백틱을 떼어 인덱스로 쓴다.
