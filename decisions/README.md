# 설계 결정 기록

무엇을 왜 그렇게 정했는지, 그리고 어떤 과정을 거쳐 거기 도달했는지 남긴다.
각 항목에 **뒤집힐 조건**을 같이 적는다. 근거가 사라지면 결정도 다시 봐야 한다.

수치는 전부 실제 세이브 파일 3개(공식 800경기 + 스크림 407경기 = 1,207경기, 챔피언 40종)를
파싱해서 측정한 값이다. 측정 스크립트는 `tools/` 에 있다.

## 오래된 문서를 믿기 전에 본다 (최근에 뒤집힌 것)

`STATUS.md` 에 있던 목록이다. 세션마다 늘어 그쪽 3KB 한도를 계속 밀어내서 여기로 옮겼다.
<b>아래 항목과 어긋나는 서술을 옛 문서에서 보면 아래가 맞다.</b>

- **시너지·카운터는 승패가 아니라 경기력에서 본다** (D63). 승패로는 805경기도 모자란다
- **챔피언 쌍은 역할군의 다른 이름이 아니다** (D64). 카운터는 `death` 로 본다
- **없는 게 아니라 안 보이는 것이다** (D62). D60 의 "2인만 실재한다" 를 그렇게 읽으면 안 된다
- **대조는 어휘가 같을 때만 작동한다** (D66). 맥락은 태그로만 준다 (D68)
- **조회수·추천수는 지어낸다** (D71). 이 저장소의 첫 예외이고 `gallery_*` 밖으로 안 나간다
- **세트 나열은 프롬프트로 못 고친다** (D72). 구조로 푼다 — 글을 짧게 여러 개로
- **갤러리는 기사에 안 매달린다** (D73). D72 결정 1 을 고친다 — 기사가 관문이 됐다
- **생성은 요청 밖에서 돈다** (D73). 몇 분 걸리는 일을 동기로 하면 "멈춘 것" 처럼 보인다
- **이슈(뉴스)는 안 만든다** (D74). D73 결정 4 를 뒤집는다 — 호출 하나 값이 시간의 절반이었다
- **조각은 둘이다** (D74). 넷은 프롬프트를 네 번 실어 보내 오히려 느렸다
- **새 갤러리는 첫 페이지가 아니다** (D75). 생성기가 고르는 매치는 늘 과거다 —
  끝난 뒤에는 페이지 번호가 아니라 배치 번호로 연다
- **`@Repository` 의 인자 검증은 `IllegalArgumentException` 으로 안 나간다.** 예외 변환이
  `InvalidDataAccessApiUsageException` 으로 바꾼다(원인은 남는다). DAO 를 부르는 쪽에서 걸린다

## 과정 요약

처음 출발점은 "경기 결과 스크린샷을 OCR로 읽어 티어표를 만든다"였다.
그런데 세이브 파일을 열어보니 게임이 이미 모든 것을 구조화해서 저장하고 있었고,
그 순간 프로젝트의 성격이 **수집 문제에서 분석 문제로** 바뀌었다.

이후 결정은 대부분 "게임이 이미 해주는 것"과 "게임이 못 하는 것"을 가르는 작업이었다.

```
OCR 전제 설계
   ↓ 세이브 파일이 평문 BinaryFormatter임을 확인
세이브 파싱으로 전환
   ↓ 4v4, 라인 없음, 역할군 5종 확인
스키마 전면 수정
   ↓ 세이브가 현재 시즌만 보관함을 확인
"시즌 누적"이 프로젝트의 핵심 가치가 됨
   ↓ 패치가 커리어마다 고유 생성됨을 확인
패치 처리를 챔피언 버전 기준으로 전환
   ↓ 효과 크기와 조합 집중도를 측정
표본 기준 10경기 + 축소추정 정렬로 확정
```
