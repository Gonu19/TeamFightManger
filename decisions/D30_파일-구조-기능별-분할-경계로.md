## D30. 파일 구조: 기능별 분할, 경계로 규칙을 강제한다 (2026-08-25)

상세는 `structure.md`. 여기에는 판단만 적는다.

**`parser/` 에 Spring 의존을 0 으로 둔다.** 조용히 틀릴 위험이 가장 큰 코드다
(`& 0xFF`). Spring 컨텍스트 없이 순수 JUnit 으로 골든 파일과 대조할 수 있어야
검증이 빠르고 확실하다. 라이브러리처럼 취급한다.

**`ingest/`(JPA)와 `analysis/`(JdbcTemplate)를 패키지로 가른다.** D22 의 규칙인데
같은 패키지에 두면 지켜지지 않는다. **문서에만 적힌 규칙은 지켜지지 않는다** —
파일 위치로 강제한다.

**`draft/` 를 `analysis/` 아래에 두지 않는다.** 시뮬은 집계값을 소비할 뿐 생산하지 않는다.

**빌드 DSL 은 Groovy(`build.gradle`).** Kotlin DSL 이 요즘 기본값이지만 이 프로젝트의
목적 중 하나가 Spring 학습이고, 학습 자료 대부분이 Groovy 다. 학습 대상이 아닌 곳에서
문법 하나를 더 배우게 만들 이유가 없다.

**`schema.sql` 을 `db/migration/V1__init.sql` 로 옮기고 루트 사본을 없앴다.**
440줄 DDL 이 두 벌이면 반드시 어긋나고, 어느 쪽이 진짜인지 애매해지는 순간
"바꾸면 마이그레이션을 추가한다"는 규칙이 무너진다. 원본은 하나다.

**빈 클래스를 미리 깔지 않는다.** `structure.md` 의 트리는 목표이고, 파일은 필요할 때 만든다.
