## D54. 팀은 공식전에서만 식별된다. 스크림에는 붙이지 않는다 (2026-08-28)

**논점.** 사용자가 팀별 통계를 요청했다. 그런데 `team` 테이블이 비어 있고
`match_record.blue_team_id` / `red_team_id` 가 전부 NULL 이었다 — **파서는 읽고 있는데
적재가 버렸다.** `SaveLoader` 에 `match.setTeams(null, null, blueScore, redScore)` 라고
적혀 있었다. 스키마도 `TeamRepository` 도 처음부터 있었다. 이어붙이지 않은 것뿐이다.

**측정 — 세이브에 무엇이 있나.** 골든 파일(`slot_638683925954242004`, 공식 294 · 스크림 181):

| | 값 |
|---|---|
| `GameStat.BlueTeamID` / `RedTeamID` | 23종. 0(플레이어) 62회 · 35번 66회 · 36번 58회 … |
| `ScrimStat.TeamID` | **181건 전부 0** |
| 팀 이름 | 경기 스트림(스트림 1)에 없다 |

**결정 1 — 공식전에만 팀을 붙인다.** `ScrimStat.TeamID` 는 전부 0, 즉 **플레이어 팀 자신**이다.
상대 번호가 어디에도 없고, 두 진영 중 어느 쪽이 플레이어인지도 세이브가 말해주지 않는다.
없는 것을 추측해 채우면 팀별 통계가 조용히 틀린다 — 스크림은 NULL 로 남긴다.

이건 손해가 아니다. 팀별 통계에서 의미 있는 것은 공식전이고, 스크림은 상대가 늘 같은
연습 상대라 팀 승률의 분모로 쓸 값이 아니다.

**결정 2 — 번호가 없으면 팀도 없다.** `gameTeamId == null` 이면 `null` 을 돌려준다.
`int` 로 받아 기본값 0 으로 떨어지면 **번호 없는 경기가 전부 플레이어 팀 경기로 둔갑한다.**
플레이어 팀은 화면에서 가장 많이 보게 될 팀이라, 이 오염은 눈에 안 띄면서 제일 아프다.

**결정 3 — 팀 이름은 비워 둔다.** 경기 스트림에 없다. 다른 스트림(0 = 미리보기)에 있을 수는
있지만 확인하지 않았다. `team.name` 은 NULL 이고, 화면은 당분간 번호로 보여준다.
**모르는 것을 "팀 36" 같은 문자열로 채워 아는 것처럼 만들지 않는다.**

**결정 4 — `TeamRegistry` 는 빈이 아니다. 적재 한 번에 하나씩 만든다.**
경기마다 조회하면 왕복이 경기 수만큼 늘어 캐시가 필요한데, **캐시를 빈에 두면 트랜잭션보다
오래 산다.** `SaveLoader` 가 롤백되면 팀 행은 사라지고 캐시에는 그 `team_id` 가 남아,
다음 적재가 없는 키를 참조한다. 수명을 트랜잭션에 맞추는 가장 확실한 방법은
트랜잭션 안에서 만드는 것이다.

`SlotRegistry` 와 이름은 닮았지만 **트랜잭션 성격이 정반대**다. 슬롯은 적재가 실패해도
남아야 하고(실패 기록이 참조한다), 팀은 적재가 실패하면 같이 사라져야 한다.

**결정 5 — 백필은 적재 경로 안에서 한다.** 팀 없이 이미 들어간 경기가 수천 건이다.
그런데 평소 경로로는 그 행을 다시 지나갈 수 없다 — `ingest_run` 의
`UNIQUE(slot_id, file_hash)` 가 같은 내용을 먼저 걸러낸다.

두 갈래를 놓고 골랐다:

| | 별도 백필 SQL | 적재 경로에서 채우기 |
|---|---|---|
| 규칙이 사는 곳 | 두 곳 (따로 늙는다) | 한 곳 |
| D35 형식 필터 | 다시 써야 한다 | 그대로 적용된다 |
| 팀 번호의 출처 | **DB 에 없다** — 세이브를 읽어야 한다 | 이미 읽고 있다 |

세 번째가 결정적이다. 팀 번호는 DB 어디에도 없으므로 어떤 백필이든 **세이브를 다시 읽어야
한다.** 그러면 적재 경로를 쓰는 것이 맞다. `SaveLoader.saveGames` 가 이미 적재된 경기를
만나면, 팀이 비어 있을 때만 채운다.

**이미 팀이 붙은 경기는 덮지 않는다.** 덮으면 재적재가 값을 바꿀 수 있게 되고,
"같은 파일을 다시 적재해도 아무것도 안 바뀐다" 는 계약이 깨진다.
점수도 건드리지 않는다 — 그래서 `setTeams` 와 `assignTeams` 를 나눴다. 고치러 와서
멀쩡한 것을 깨는 경로를 아예 만들지 않는다.

**결정 6 — `tfm.reingest-on-start` (기본 꺼짐).** 백필을 실제로 돌리려면 해시 검사를
건너뛰어야 한다. `ReingestRunner` 가 `SaveLoader.load()` 를 직접 부른다 — 우회하는 것은
해시 검사 하나뿐이고 적재 규칙은 한 벌 그대로 쓴다.

게임을 계속 하는 슬롯은 해시가 바뀌어 저절로 따라잡히지만, **손대지 않는 커리어는 영원히
비어 있는 채로 남는다.** 커리어 3개 중 2개가 그 상태다 — D39 가 잡은 것과 같은 종류의 누수다.

`ingest_run` 은 남기지 않는다. 새로 적재한 것이 없기 때문이다. 억지로 남기면 유니크 위반으로
죽거나, 해시를 비틀어 "이 내용은 적재됐다" 는 기록을 두 벌로 만든다. **이건 적재가 아니라
수리다.** 다시 돌리면 백필 0건을 찍는다 — 그게 다 됐다는 신호다.

**검증.** DB 없이 도는 테스트 10개(`TeamRegistryTest` · `ReingestRunnerTest`)를 변조 4종으로
확인했다 — null 가드 제거 · 캐시 제거 · 기존 팀 재사용 제거 · 첫 슬롯에서 루프 중단.
넷 다 잡혔다. 픽스처가 필요한 3개(`IngestServiceTest` 의 D54 절)는 **아직 변조로 확인하지
않았다** — 워크트리에 `fixtures/*.tfm` 이 없어 건너뛰어진다. 메인에서 돌려야 한다.

**주의 — `ApplicationRunner` 실행 순서는 정의되어 있지 않다.** 「아직 안 정한 것」의 집계
트리거 항목과 같은 함정이다. `tfm.reingest-on-start` 와 `tfm.aggregate-on-start` 를 **같이
켜지 마라.** 집계가 재적재보다 먼저 끝나면 팀이 아직 비어 있는 상태로 집계된다.
수리 한 번, 집계 한 번 — 두 번 띄운다.

**아직 안 한 것.** 팀별 집계와 화면은 없다. 적재가 먼저다 — 채워지지 않은 컬럼 위에
집계를 얹으면 "0건" 과 "안 돈다" 를 구별할 수 없다.

**뒤집힐 조건.** 다른 스트림에서 팀 이름을 찾으면 결정 3 이 바뀐다.
스크림에 상대 팀 번호를 담는 필드를 찾으면 결정 1 이 바뀐다.
