## D37. 성능은 재고 나서 고친다 (2026-08-26)

리뷰가 "행마다 SELECT+INSERT 가 나간다", "배치가 안 걸린다" 를 지적했다. 그럴듯했지만
**코드만 읽고 낸 추론**이었다. 이 프로젝트는 데이터로 확인할 수 있는 것을 추측하지 않는다.

**측정했다** (`IngestCostTest`, slot_638683 · 경기 475건).

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| JDBC statement | 11,901 | **1,310** |
| 경기당 | 25.1 | **2.8** |
| 엔티티 INSERT(행) | 6,181 | 6,181 |

**지적이 맞았고, 그것도 거의 정확히 맞았다.** 여분 SQL 5,720개는 `@EmbeddedId` 행 수
(참가자 3,800 + 밴 1,764 + 패치이벤트 ≈ 5,714)와 거의 일치했다 — **행 하나당 SELECT 하나씩**
더 나가고 있었다.

**원인.** `@EmbeddedId` 는 ID 가 미리 채워져 있어 Spring Data 의 기본 판정이 "기존 행" 이 된다.
그러면 `save()` 가 `persist()` 가 아니라 `merge()` 를 부르고, INSERT 전에 SELECT 를 한 번 더 낸다.
**있을 리 없는 행을 매번 확인한 것이다.**

**고친 것.** `Persistable<ID>` 구현(`isNew()` 항상 true) + `hibernate.jdbc.batch_size: 50`.
이 세 테이블은 적재에서만 쓰고 수정하지 않으므로 안전하다. 같은 키를 두 번 넣으면
유니크 제약에서 크게 실패한다 — 조용히 덮어쓰지 않는다.

**측정 코드 자체에도 버그가 있었다.** `엔티티 수 − statement 수` 로 "SELECT 수" 를 구했는데,
배치가 걸리면 엔티티 여러 개가 statement 하나로 묶이므로 그 뺄셈이 성립하지 않는다.
음수가 나와서 알았다. **재는 도구도 틀릴 수 있다.**

**임계값을 걸지 않았다.** 무엇이 정상인지 모르는 채 임계값을 걸면 방어선이 아니라
현재 상태의 박제다. 숫자를 출력하고 사람이 본다.
