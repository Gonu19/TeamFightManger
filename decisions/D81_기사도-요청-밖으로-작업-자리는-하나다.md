# D81. 기사도 요청 밖으로 · 작업 자리는 하나다

**날짜:** 2026-09-02
**고치는 것:** 기사 생성이 동기 POST 였던 것. 그리고 갤러리만 갖고 있던 작업 잠금.

---

## 왜

D73 이 갤러리를 요청 밖으로 뺐다. 이유는 이랬다.

> 페이지 하나가 모델 호출 다섯이고 분당 토큰이 8,000 이라 최소 3분이다. 요청 스레드
> 안에서 하면 브라우저는 스피너만 돈다 — 사용자에게 그것은 "멈췄다" 와 구분되지 않는다.

**기사는 그대로 두었다.** 호출이 둘이라 짧다는 것이 이유였을 텐데, 짧아도 20~30초다.
그동안 브라우저는 흰 화면을 물고 있고, 429 를 한 번 맞으면 더 간다. 같은 병인데
한쪽만 고쳐 둔 셈이었다.

그리고 더 나쁜 것이 있었다. **잠금이 갤러리에만 있었다.** 갤러리가 도는 중에 기사
버튼이 멀쩡히 눌렸고, 둘이 동시에 돌면 분당 토큰을 서로 잡아먹어 <b>둘 다 느려지고
실패 확률만 올랐다.</b> 두 배 빨라지는 것이 아니다.

---

## 결정

### 1. 작업 자리는 커리어당 하나. 종류를 안 가린다

`GalleryJobs` 를 `StoryJobs` 로 옮기고 기사·총평·갤러리가 같은 자리를 쓰게 한다.
갤러리가 도는 중에 기사를 누르면 거절하고, 그 반대도 같다.

**거절은 예외가 아니다.** 버튼을 두 번 누르는 것은 오류가 아니라 흔한 일이다.
화면이 "기사를 이미 뽑는 중이다" 라고 말하면 된다 — **무엇이 도는지를 말하는 것이
중요하다.** "이미 돌고 있다" 만 쓰면 사용자는 자기가 방금 누른 것이 시작된 줄 안다.

잠금은 **커리어 단위**다. 슬롯이 다르면 서로 막지 않는다.

### 2. 화면이 과정을 그린다

```
기사 — 기사를 쓰는 중      0/2
기사 — 댓글을 다는 중      1/2
기사 — 대조하고 저장하는 중  2/2
```

`Progress` 를 `GalleryWriter` 밖으로 꺼내 공용으로 두고, `ArticleWriter` 가 단계마다
알린다. 화면은 2초마다 `/story/status` 를 물어 막대를 갱신하고, 도는 동안 생성 버튼을
전부 잠근다.

**서버도 같은 것을 막는다.** 화면이 잠그는 것은 그 거절을 <b>미리 보이게</b> 하려는
것뿐이다 — 눌러야 "이미 도는 중" 을 알게 되는 버튼은 버튼이 아니다.

### 3. 실패는 원인까지 화면에 남긴다

`FAILED` 상태가 메시지를 들고 있고, 화면이 진행 막대 자리에 그것을 그린다.

**맨 밑의 원인까지 내려간다.** 감싸인 예외의 겉껍질만 보여주면
`UncheckedIOException` 같은 말이 뜨는데, 그걸로는 사용자가 할 일을 못 정한다 —
키가 없다 · 파일이 없다 · 429 가 안 풀린다 는 서로 다른 대응을 요구한다.

실물 확인(잘못된 키로):

```
실패 — 기사를 못 만들었다
StoryFailedException: 모델이 401 로 응답했다: {"error":{"message":"Invalid API Key", …
```

"할 일이 없다"({@code NOTHING_TO_DO})는 실패가 아니고, **종류마다 문구가 다르다.**
"뽑을 매치가 없다" 를 기사에 그대로 쓰면 사용자가 할 일을 못 찾는다 — 기사가 빈손인
것은 세이브에서 그 매치를 못 찾았다는 뜻이다.

### 4. 끝나면 결과로 데려간다. 다만 **내가 시작한 것만**

D74 가 이미 이 함정을 밟았다. 끝난 상태는 서버 메모리에 남으므로(그래야 화면을 늦게
열어도 결과를 볼 수 있다) `DONE` 을 볼 때마다 이동하면 <b>이동 → 폴링 → DONE → 이동</b>
이 끝없이 돈다.

그래서 갤러리와 같은 규칙을 쓴다: `sessionStorage` 에 "내가 눌렀다" 를 남기고,
그 표식이 있을 때만 결과로 넘어간다. 표식은 폼이 **실제로 제출될 때** 남긴다.

`sessionStorage` 가 막히면(사생활 보호 모드) 표식이 비어 **이동을 아예 안 한다** —
결과를 자동으로 못 보는 것은 불편하지만 루프가 도는 것보다 낫다.
실패 방향을 안전한 쪽으로 둔다.

### 5. `POST /story/generate` 를 걷어낸다

"아직 안 쓴 매치 중 가장 최근 것" 을 동기로 쓰던 입구다. 화면이 매치를 줄로 세운
뒤로(D79) 부르는 곳이 없어졌고, 남겨 두면 주소로는 여전히 닿는 **30초짜리 동기 경로**가
된다 — 진행 상황도 없고 작업 잠금도 안 거치는, 이번에 고치려던 바로 그 길.

고르는 규칙 자체는 안 사라졌다. `StoryGenerator.writeLatestUnwritten` 이 그대로 있고
`StoryGeneratorTest` 가 그것을 지킨다. 없어진 것은 **그 규칙으로 가는 HTTP 문**뿐이다.

### 6. 집계 버튼은 이 잠금을 안 쓴다

`POST /story/aggregate` 는 요청 안에서 돈다. **1초 남짓이고 바깥으로 안 나간다** —
분당 토큰을 안 쓰므로 다른 생성과 경쟁하지 않는다. 잠금에 넣으면 얻는 것 없이
"집계 중에는 기사를 못 쓴다" 는 제약만 생긴다.

## 조사·문구

종류 이름에 조사를 붙여 둔다(`기사를` · `총평을` · `갤러리 반응을`). 코드로 이어
붙이면 "기사 를" 처럼 띄어지고, 받침에 따라 을/를 이 갈리는 것도 못 맞춘다("총평를").
낱말마다 한 번 적는 편이 규칙을 흉내 내는 것보다 짧고 확실하다 — 종류가 셋뿐이다.

---

## 확인한 것 / 못 한 것

**확인:** 잘못된 키로 실물 실행. 버튼 87개가 붙고, 눌러도 즉시 목록으로 돌아오고,
진행 막대가 뜨고, 401 원인이 화면에 남고, 닫기 버튼이 생긴다. 상태 조회는 생성이
꺼져 있어도 200/`IDLE` 이다 — 404 를 주면 폴링이 콘솔을 빨갛게 물들이고 그건 고장으로 읽힌다.

**못 함:** 진행 중 상태를 브라우저에서 눈으로 못 봤다. 401 이 1초 안에 끝나기 때문이다.
잠금과 단계 전이는 `StoryJobsTest` 가 가짜 생성기로 고정한다.

## 뒤집힐 조건

- **유료 티어로 올라가면** — 분당 토큰이 넉넉해지면 결정 1(자리 하나)의 근거가 약해진다.
  그때도 같은 매치를 두 번 뽑는 것은 막아야 하므로 잠금이 **매치 단위**로 내려갈 수 있다
- **앱이 여러 사용자를 받게 되면** — 상태를 메모리에 두는 것(D59 전제)이 무너진다.
  그때는 작업 상태도 저장돼야 하고, "재시작하면 진행 중이 거짓말이 된다" 를 다시 풀어야 한다
- **생성이 몇 초로 줄면** — 진행 막대가 깜빡이기만 하고 읽히지 않는다. 그때는 막대 대신
  버튼 안의 회전 표시가 맞다
- **호출 수가 종류마다 달라지면** — 지금은 기사·총평이 둘, 갤러리가 조각 수만큼이다.
  `CALLS` 상수가 그 가정을 들고 있다
