## D46. 집계 조회는 행만 꺼낸다 — 전개도 감쇠도 SQL 에 넣지 않는다 (2026-08-27)

**논점.** 쌍 전개(승리 팀 4명 × 패배 팀 4명)와 감쇠 가중치를 SQL 로 하면 한 번의 쿼리로
집계가 끝난다. `self join` 과 `power(0.5, ...)` 로 충분히 쓸 수 있다.

**결정.** SQL 은 참가자 행을 꺼내는 일만 한다. 전개·감쇠·축소는 전부 Java 순수 함수다.

**이유.** **DB 없이 변조로 검증할 수 있는지가 갈림길이다.** "아군끼리는 쌍이 안 생긴다",
"양방향 가중치가 같다", "두 챔피언의 변경 횟수를 합친다" 같은 것은 조인 하나만 어긋나도
깨지는데 결과는 여전히 0~1 사이의 그럴듯한 승률이다. SQL 안에 있으면 실제 DB 를 띄워야만
확인할 수 있고, 그건 Claude 가 비밀번호를 넣지 못해 사용자 손을 거쳐야 한다는 뜻이다 —
검증 주기가 느려지면 변조 검증(D40)이 실제로는 안 돌아간다.

**비용은 작다.** 경기 1,200건에 참가자 8명이면 1만 행이다. 전부 메모리에 올려도 몇 MB 고,
쌍으로 펴도 2만 개다. D37 이 정한 대로 성능은 재고 나서 고친다.

**SQL 이 조용히 틀리는 자리는 따로 있다.** 전개가 아니라 **무엇이 빠지는가** 다.
`patch` 조인이 INNER 면 커리어 시작 직후 경기가 통째로 사라지고, `include_scrim` 조건이
빠지면 스크림이 공식전 표에 섞인다. 둘 다 예외를 내지 않고 "데이터가 좀 적네"·"승률이 좀
이상하네" 로만 보인다. 그래서 DAO 테스트는 정확성이 아니라 **누락**을 겨냥해 썼다.

**`team_size = 4` 필터는 두 번째 방어선이다.** 처음엔 이것도 같은 종류의 누락 위험으로 봤는데,
테스트를 돌려보니 V2 의 `CHECK (team_size = 4)` 때문에 비4v4 경기는 **DB 에 들어오지도
못한다.** 규칙이 문서가 아니라 제약으로 있는 것이다(D35 가 의도한 그대로다). 그래도 필터는
남긴다 — D35 의 뒤집힐 조건이 실현돼 2·3인 경기를 다시 적재하게 되면, 그때 카운터 집계가
그것을 섞지 않게 막는 것은 이 필터뿐이다. 제약을 트랜잭션 안에서만 떼어내 그 상황을 만들고
필터가 실제로 걸러내는지 확인했다.

**기준 시점의 누적 변경 횟수는 적재와 같은 방식으로 센다.** `SaveLoader` 는
`champion_patch_event` 를 전부 세고 `is_new` 를 뺀 적이 없다. 집계에서만 걸러내면
두 누적의 기준이 어긋나 그 차이가 그대로 감쇠 지수로 들어간다.

**뒤집힐 조건.** 슬롯이 수십 개가 되거나 경기가 수십만 건이 되면 메모리 전개가 안 맞는다.
그때는 SQL 로 내리되, 지금의 순수 함수를 골든 값 생성기로 써서 두 결과를 대조한다.
